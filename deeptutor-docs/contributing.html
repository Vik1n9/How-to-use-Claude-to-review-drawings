DeepTutor 玩得多了，總有朋友手癢想給這個開源專案遞點程式碼，或者順手修個 bug。

正好，官方文件裡有一頁專門講怎麼參與貢獻，我把要點全部搬過來了：路線圖在哪看、程式碼該提到哪個分支、環境怎麼搭、提交訊息怎麼寫，一條不落。

先提醒一個最容易踩的坑：這個專案用的是多分支模型，不要把 PR（合併請求）提到 main，預設目標是 dev 分支，拿不準就提 dev。

但是問題來了。給開源專案貢獻程式碼和自己閉門寫專案不太一樣，編碼規範、提交格式、評審標準全是硬性檢查，亂來的話 PR 很容易被卡住。

下面這份指南照著走，基本一次過。

路線圖

DeepTutor 的公開路線圖維護在 HKUDS/DeepTutor#498。你可以在那裡檢視計畫中的工作、表達優先順序、或在開始較大的貢獻前提出新方向。

PR 應該提到哪個分支

分支 適合
dev 預設目標 —— 新功能、重構、bug 修復、API / 設定改動
multi-user 僅限多租戶 / session 隔離 / 共享工作區相關工作

拿不準就提到 dev。

快速上手

# 1. Fork + clone，先与目标分支同步
git checkout dev && git pull origin dev

# 2. 拉新分支
git checkout -b feature/your-feature-name

# 3. 编辑模式安装全套
pip install -e ".[all]"

# 4. 配置 pre-commit（每台机器一次）
pip install pre-commit
pre-commit install

# 5. 改完跑一遍校验
pre-commit run --all-files

# 6. 把 PR 提到 dev（或 multi-user）

可以從 good first issue 標籤找入手點。開工前先在 issue 下留言，避免重複勞動。

編碼規範

CI 會強制檢查；pre-commit run --all-files 在本機能查出大部分問題。

範疇 規則
Python 所有函式簽章加 type hint；遵循 PEP 8（Ruff 強制）；用 f-string；保持函式小而專一
Docstring 新模組 / 類 / public 函式使用 Google 風格 docstring
Secrets 嚴禁提交；每個 PR 上 detect-secrets 都會跑
Subprocess 永遠用 shell=False
路徑 pathlib.Path 優於字串串接

底層工具鏈：Ruff（lint + format）、Prettier（前端 / 設定）、detect-secrets、pip-audit、Bandit、MyPy、Interrogate。

這套檢查說實話相當嚴格，但也正因為管得嚴，主儲存庫才能一直保持得這麼幹淨，對認真貢獻的朋友來說反而是件香事。

Commit message 格式

<type>: <short description>

[optional body]
Type 用法
feat 新功能（MINOR 版本跳一格）
fix bug 修復（PATCH 版本跳一格）
docs 僅文件
style 僅格式化
refactor 重構，無行為變化
test 增 / 改測試
chore 建置 / 工具鏈 / 依賴

評審會看什麼

  • 正確性 —— 是否真的解決了問題？是否引入迴歸？
  • 範圍 —— 小而聚焦的 PR 比龐大雜燴 PR 合得快；拿不準就拆。
  • 測試 —— 新行為要有對應覆蓋；bug 修復儘量帶回歸測試。
  • 文件 —— 影響使用者的改動要同步更新 site/src/content/docs/ 下的相關頁面。

尋求幫助

  • Discord —— 提問最快的地方
  • GitHub Discussions —— 長篇問答
  • 微信社群 —— 中文貢獻者群
  • Issues —— bug 反饋與功能建議

參考

  • CONTRIBUTING.md —— 完整文件（分支策略、安全實踐、維護者）
