原文連結：https://docs.deeptutor.info/zh-cn/get-started/troubleshooting/

前面幾篇把 DeepTutor 的 4 種安裝方式都過了一遍，留言區也開始熱鬧起來，各種報錯截圖往上貼。

DeepTutor 官方文件裡有一頁專門的排錯手冊，把常見錯誤按 9 大類分組，每一條都給了可以直接複製貼上的修復命令。不管你裝的是 PyPI（Python 官方包儲存庫）、原始碼、Docker（容器部署工具）還是僅命令列工具（CLI）版，都適用。

但是問題來了。報錯資訊五花八門，很多人卡在這一步就直接放棄了。其實第一步永遠只有一個：如果你的安裝行為不太對勁，先跑一次 deeptutor doctor 看缺了什麼。然後在下面對號入座，解法全部保留原樣，照抄就行，穩到不行。

一、連接埠與行程

Address already in use :3782 （或 :8001）

有別的東西綁定到這個連接埠了。找出來：

# macOS
lsof -i :3782

# Linux
ss -ltnp | grep :3782

# Windows PowerShell
Get-NetTCPConnection -LocalPort 3782

幹掉它，或者透過重跑 setup 精靈或編輯 data/user/settings/system.json 改 DeepTutor 連接埠：

deeptutor init
{
  "backend_port": 18001,
  "frontend_port": 4000
}

如果只是一次性行程級覆蓋，啟動 DeepTutor 之前在 shell 裡 export 環境變數即可：BACKEND_PORT=18001 FRONTEND_PORT=4000 deeptutor start。

如果在用 Docker，改 docker 專用的連接埠變數：

DEEPTUTOR_DOCKER_FRONTEND_PORT=4000
DEEPTUTOR_DOCKER_BACKEND_PORT=18001

後端起來了但前端連不上

前端會在伺服器端把 /api/* 和 /ws/* 轉發給後端，所以當你以另一個 hostname 提供服務時（雲部署、區域網路訪問、反向代理），瀏覽器只用前端 origin 即可，把使用者端和反向代理都指向前端連接埠就行，不需要設定任何 API base。

只有拆分部署（後端和前端分開跑）才需要顯式設定 API base。開啟 設定 -> Network，或把 data/user/settings/system.json 裡的 next_public_api_base 設成前端伺服器訪問後端用的內部網路地址，然後重新啟動：

{
  "next_public_api_base": "http://backend:8001"
}

next_public_api_base_external（及其別名 public_api_base）作為更低優先順序的退回被接受。

如果認證已開啟且前端 origin 與 API origin 不同，也要設定精確跨域（CORS）origins：

{
  "cors_origins": ["https://deeptutor.example.com"]
}

二、LLM / Embedding 服務商

provider probe 時報 HTTPError 401 Unauthorized

服務商（Provider）拒絕了你的 API 金鑰（API key）。常見坑：

  • OpenAI ：以 sk- 開頭（project key 以 sk-proj- 開頭）
  • Anthropic ：以 sk-ant- 開頭
  • Azure OpenAI ：在 設定 → Models → LLM 的當前 profile 中填寫 API Version
  • Google Gemini ：以 AIza 開頭
  • Ollama / 本機 OpenAI 相容 ：API key 留空或用 none ，base URL 設成像 http://localhost:11434/v1

重跑 deeptutor init 重新輸入 key，或者直接編輯 data/user/settings/model_catalog.json。

設定時 Failed to fetch /models

DeepTutor 會 ping provider 的 model-list 端點來填充模型下拉框。如果你的網路把它擋了，會出現這個警告，這是非致命的。精靈會 fallback 到一份硬編碼的常見模型列表然後繼續。

host.docker.internal 解析不了（Docker + 本機 Ollama）

宿主系統 用
macOS、Windows http://host.docker.internal:11434/v1
Linux http://172.17.0.1:11434/v1 （docker0 網橋） 或宿主機的 LAN IP

Linux 使用者也可以手動加 host.docker.internal：

services:
  deeptutor:
    extra_hosts:
      - "host.docker.internal:host-gateway"

查詢 KB 時報 Embedding dimension mismatch

你用不同的向量化模型（Embedding）重建了知識庫（KB）。快取裡的維度對不上了。

修復：在 Web UI 裡，Knowledge → 選 KB → Index versions → Re-index now。重建索引沒有暴露成 CLI 命令。

Embedding endpoint URL 老是出錯

Embedding adapter 會原樣使用 profile 的 Base URL，因此請在 設定 → Models → Embedding 中填寫完整 endpoint，而不是只填 API root：

Provider 錯誤 正確
OpenAI https://api.openai.com/v1 https://api.openai.com/v1/embeddings
Cohere https://api.cohere.com https://api.cohere.com/v2/embed
Jina https://api.jina.ai/v1 https://api.jina.ai/v1/embeddings

三、知識庫

KB 卡在 indexing 狀態

索引是後台任務跑的。看日誌：

tail -f data/user/logs/deeptutor.jsonl | grep -i kb

常見原因：embedding provider 回傳 429（限流，用更小的 batch 重試）、embedding host 不可達（檢查網路）、或者 PDF parser 失敗（確認檔案沒有密碼保護）。

重建索引修不了維度不匹配

如果重建索引之後維度不匹配仍然存在，KB store 裡可能有過期的設定檔案。從 CLI：

deeptutor kb delete physics --force
deeptutor kb create physics --doc chapter1.pdf

四、多使用者

重新啟動之後每個 API 呼叫都報 401 Unauthorized

data/system/auth/auth_secret 丟失或被重新生成了，所有 JWT 都失效了。

修復：從備份還原 data/system/auth/auth_secret，或接受新的 secret 並讓所有使用者重新登入。專案根目錄 .env 不會被執行環境自動載入。

第一個使用者沒被提升為 admin

編輯 data/system/auth/users.json，把那個使用者的 "role": "admin" 設好，然後重新啟動。

登入成功但又跳回 /login

認證 cookie 沒被設定上，通常因為：

  1. auth.json: cookie_secure=false 但你是跨站 HTTPS 部署 —— 設成 true 後重新啟動，讓 cookie 使用 SameSite=None; Secure
  2. 本機 HTTP 測試時誤設了 cookie_secure=true —— 改回 false
  3. 瀏覽器攔了第三方 cookie，而你在子域上 —— 把前端和 API 部署在同一個 hostname 下（比如都在 deeptutor.example.com ，前端在 / ，API 透過 /api/ 代理）

五、Docker

容器立刻退出

docker logs deeptutor | tail -30

原始碼樹 Compose 部署應保留 ./data:/app/data bind mount；重試 wrapper 前先檢查宿主機路徑權限：

mkdir -p data
python scripts/docker_compose.py up -d

容器是 Running 但是 unhealthy

健康檢查會從容器內探測後端，並設定了 60 秒 start period。如果啟動更久，容器可能變成 unhealthy。

如果狀態一直不恢復，直接執行映像檔內建的 healthcheck，並檢視容器日誌：

docker exec deeptutor python /app/healthcheck.py
docker logs deeptutor | tail -40

建置時 npm install 逾時

Next.js 依賴樹很大。調大 npm 的網路逾時：

npm config set fetch-timeout 600000

官方 Dockerfile 已經設了，只在本機建置時才需要管。

六、Python 安裝

Microsoft Visual C++ 14.0 is required （Windows）

某個依賴退回到了 Windows 原始碼建置。安裝 Build Tools for Visual Studio，勾選 “Desktop development with C++” workload，然後重試安裝。

libolm not found （僅 Matrix E2EE 需要）

# macOS
brew install libolm

# Debian / Ubuntu
sudo apt install libolm-dev

# 重装 matrix-e2e extra
pip install -e ".[matrix-e2e]" --force-reinstall

pip install 慢到爆

網路慢的話，用本機 PyPI 鏡像站或 wheelhouse。中國大陸使用者：

pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple

Conda 環境已啟用但 python 仍然指向別處

PATH 順序可能蓋住了 conda 的 python。驗證：

which python

如果不是，在一個新 shell 裡跑 conda activate deeptutor。

七、前端

前端顯示空白頁

開啟瀏覽器開發者工具（⌥⌘I），看 Console 標籤頁。常見原因：

  • CORS errors —— 前端一個 origin，後端另一個 origin，而後端沒把這個前端 origin 加進允許列表。編輯 data/user/settings/system.json ，把你的前端 origin 加進 cors_origins 。
  • /_next/... 404 —— 靜態 bundle 沒建置。從原始碼起的話： cd web && npm run build 。
  • 後端連不上 —— 驗證 curl http://localhost:8001/ 是否回傳 JSON。

每個頁面都彈 “Failed to fetch” toast

跟上面一樣，通常是後端沒起來或者 CORS / API base URL 對不上。看 Network 標籤頁確認請求實際去了哪個 URL。

八、Partners 與管道

Partner channel 在 Channels 面板置灰 / 報 “missing SDK”

某個管道的開發工具包（SDK）import 不進來時，Partners 的 Channels 面板會把該 channel 置灰並顯示 import 錯誤（如 No module named 'lark_oapi'）；從 CLI 啟動 partner 也會報同樣的錯。裝上缺的依賴集，然後重新啟動 DeepTutor：

pip install -e ".[partners]"           # 全部内置 channel SDK（源码安装）
pip install -U "deeptutor[partners]"   # PyPI 安装用这条
pip install -e ".[matrix]"             # Matrix channel；加密房间用 ".[matrix-e2e]"（需要 libolm）

如果你用的是 packaging/deeptutor-cli 的純 CLI 包（它沒有定義任何可選元件 extras），改從原始碼 checkout 裝 requirements 鏡像：

python -m pip install -r requirements/partners.txt

裝好包、重新啟動 server 之後該 channel 即恢復。

Partner 連上了但不回應

檢查 channel card 裡的 allow_from：

weixin:
  enabled: true
  allow_from:               # 空 = 全部拒绝
    - "*"                    # 允许所有人
    # - "sender-id"          # 测试后换成具体 user/chat ids

預設 allow_from: [] 拒絕所有人，你必須顯式 opt in。

Channel 跑幾分鐘就掉線

長輪詢（long-poll）/ WebSocket 連線偶爾會掉。channel manager 會帶退避自動重連，但如果你看到頻繁掉線：

  • 檢查宿主機和 gateway provider 之間的網路穩定性
  • WeChat 檢查 state_dir 是否可寫、是否持久化
  • Teams / webhook 類 channel 檢查對外網路 callback URL 是否能到達設定的 host/port/path
  • Matrix 檢查 homeserver 是否有過於激進的逾時

針對每個 gateway 的除錯方法見 Partners 夥伴與管道 和 管道矩陣。

九、記憶 / RAG 精度

Chat 忽略了掛上的 KB

確認：

  1. KB 掛上了 這一輪（不只是在選擇器裡出現 —— 真的點進了啟用集）
  2. rag 工具由上下文控制，不會出現在 設定 → 工具；請掛載使用它的 KB（PageIndex 使用自己的工具）
  3. KB 是 status: ready （不是還在索引）—— 透過 deeptutor kb list 檢查

read_memory 回傳空

read_memory 會串接四份 L3 文件：

  • preferences 由 write_memory 直接寫入
  • recent 、 profile 、 scope 只在 Memory Workbench 中手動整合

沒有每 N 輪自動整合。

在那裡執行 Update，或透過 API 提交必填的 layer、key、mode：

curl -X POST http://localhost:8001/api/v1/memory/runs/start \
  -H 'Content-Type: application/json' \
  -d '{"layer":"L3","key":"recent","mode":"update"}'

Memory writes 被標成 unsafe_text

write_memory 接受 1 到 240 字元的偏好文字。這裡沒有 unsafe_text 結果或內容安全過濾；超過上限時縮短文字即可。
