美容儀器說明書 AI 協作工作流

這個案子的素材是一份 19 頁的簡體中文美容儀器說明書 PDF，最終交付是一份 28 頁 A4、繁體中文、含封面目錄配圖的新版手冊 PDF。中間經過三個 AI 工具接力，每個工具只做一種性質的工作。以下按時間順序記錄每一步怎麼判斷、Prompt 怎麼下、踩了哪些坑。

案前判斷：這不只是翻譯

表面任務是「PDF 翻譯成繁體中文 HTML」，但動工前先判斷出這份文件有三個風險，每一個都會讓「直接翻譯」變成錯誤做法：

  • 疑似醫療描述——原稿有大量容易被誤認為醫療行為、疾病診斷、療效宣稱的語句，必須改寫而不是照翻。
  • 簡轉繁陷阱——原稿是簡體中文，不能只做字形轉換，專有名詞與台灣常用語都要深度在地化。
  • 格式保留——說明書有章節、警告、注意事項、表格、配件清單，轉出來不能只剩純文字。

所以這個案子的目標從一開始就定義成：

輸出格式選 HTML 而不是直接做 PDF，是刻意的：HTML 比 PDF 容易事後校正與修改，等內容全部定稿，再轉成 PDF 也很方便。後面兩個階段的校稿與排版，都受惠於這個決定。

工作流總覽：計劃、開發、驗證、品管、輸出

我認為 AI 工作流程應該是：計劃 → 開發 → 驗證（審稿）→ 品管 → agent 輸出。這個案子就是照這個骨架排的，三個 AI 工具各自只負責其中一段：

工作流階段本案對應使用工具AI 的角色
計劃案前判斷風險、定義目標；排版階段另以計畫模式先核准計畫再動工人工＋AI 計畫模式—
開發PDF 翻譯、合規改寫、產出 HTML 初版Open Code 調用 DeepSeek生產者
驗證（審稿）對照原始 PDF 複驗初版，修正錯翻與醫療殘留Codex審稿者
品管排版成品逐頁目檢＋程式化斷言複驗Claude Code工程師
agent 輸出配圖整合、版面設計、A4 PDF 成品輸出Claude Code工程師

這樣分工有兩個前提，每個階段都要遵守：

  • 每階段只做一種性質的工作——產出、質檢、排版分開，Prompt 才能聚焦，出問題才能歸因。
  • 上一階段的產物永遠當草稿——每個新階段都明確告訴 AI「不要直接視為正確稿」，避免錯誤被沿用到底。

階段一：Open Code + DeepSeek 做初版

為什麼選 Open Code + DeepSeek

選它有兩個理由。第一是省 token：PDF 轉 HTML 是大量整理工作，用便宜的模型跑初版最划算。第二個理由更關鍵：原稿是簡體中文，裡面有許多疑似醫療的說明方式，直接調用其他模型時，模型無法分辨這到底是不是真的醫療內容，很容易觸發內容審查、被迫拒絕工作。所以必須交給一個能讀懂這本手冊、能判斷語境的模型，先把內容修正成合規版本，後面的工具才接得下去。

實際使用的 Prompt

這段話不長，但拆開來看，把初版需要的條件一次講齊了：

Prompt 片段目的
pdf檔案為美容儀器說明書給 AI 文件類型與上下文，避免當一般文章處理
內有大量會遭人誤會為醫療行為的敘述指出最重要的合規風險，不只是翻譯問題
請協助修正要求改寫，不是只找問題
不得直接簡轉繁＋深度轉換避免機械字形轉換，要求語意與用語層級的在地化
不確定的名詞不要硬翻譯，詢問我設下人工確認點，避免 AI 自行創造錯誤名稱
保留原有格式，製作成html檔案指定輸出格式與版面保留要求

反過來想就知道為什麼要講這麼齊：只說「幫我翻成繁體中文」，AI 會把「患者」「禁忌症」「醫療裝置」原樣留下；只說「幫我去掉醫療內容」，AI 可能連必要的安全提醒一起刪掉，或把格式打散。

初版出來後，先用肉眼看什麼

DeepSeek 產出 HTML 初版後，不要當完稿，把它當「可編輯草稿」快速檢查：章節是否大致完整、警告與表格還在不在、有沒有明顯簡體殘留、有沒有醫療用語、功能名稱有沒有被 AI 改得太漂亮太像療效宣稱。看完不要急著交付，進第二階段。

階段二：Codex 複驗校稿

第二階段把 AI 的角色從「生產者」切換成「審稿者」：不是重做，而是拿原始 PDF 和初版 HTML 對照，找出錯翻、醫療描述殘留、改寫不當，然後修正。工具選 Codex 純粹是我習慣用 Codex 校稿，換成其他 AI 工具其實不影響這個流程。

實際使用的 Prompt

這段 Prompt 的關鍵字是「重新檢查」。第二階段最容易犯的錯，是 AI 沿用初版內容、沒有真正回去比對原稿。所以要明確要求：看原始 PDF、看改寫後 HTML、找出問題；能確定的直接修，不確定的停下來問。

複驗實際抓到的問題

初版看起來已經很完整，但 Codex 對照原稿後仍然抓出好幾類問題——這正是「看起來完成，其實殘留風險」的實例：

問題類型例子為什麼要修
醫療裝置語彙「植入式心臟除顫器或其他電磁植入式醫療裝置」太接近醫療器材語境
疾病與生理指標「慢性疾病者（如血糖、血壓、血脂相關問題者）」仍像醫療禁忌或疾病診斷
功能名稱被改寫「五極彩光微電波護理」原 PDF 是「五極彩光微電」，初版自行加了療程感的詞
功能名稱不精準「水氧噴霧」原 PDF 是「水氧噴槍」
功效暗示「煥膚筆」比原名中性，但仍可能暗示膚況改善
繁中錯字或不自然「實銷性」「其它」要改成正式繁中說明書語氣

修正方向：不是刪光，而是換語氣

合規改寫的原則是保留安全提醒、拿掉醫療診斷語氣，讓文件讀起來像美容儀器產品文件，而不是醫療器材文件：

原本的語氣改寫方向
患者、疾病、感染、心臟除顫器使用者、膚況、植入式電子裝置
禁忌症不建議使用情形
血糖、血壓、血脂當日狀態不佳或需避免刺激者
皮膚感染皮膚破損、紅腫、滲液或明顯異常

功能名稱則優先改回原 PDF 的中性名稱：「五極彩光微電波護理」改回「五極彩光微電」、「水氧噴霧」改回「水氧噴槍」。涉及功效暗示的名稱另外處理，見下一段。

人工守門點：哪些地方 AI 不能自己定案

三個階段的 Prompt 都寫了同一句話：「不確定的部分詢問我。」這不是客套，而是這類任務裡真正的安全網。需要停下來問人的典型情況：

  • 功能名稱可能和機身 UI、按鈕、配件標籤一致時——改了名，使用者會對不上實物。
  • 原文名稱本身有醫療或功效暗示，但改名可能影響產品辨識時。
  • 某個詞可能是品牌專有名詞，不確定能不能改。
  • 安全提醒到底能刪除、還是只能改寫時。

本案留給人工確認的代表案例是「美斑筆」：原名容易被理解為處理斑點、改善色素，初版改成的「煥膚筆」仍有膚況改善暗示，最後改成最中性的「美容筆」——但因為這個名稱可能印在機身或包裝上，AI 不自行定案，改完明確回報，由我確認。

階段三：Claude Code 配圖與排版

為什麼這一棒換 Claude

前兩階段是「內容工程」：翻譯、合規、審稿。第三階段性質完全不同，是「排版工程」：寫程式抽圖、計算座標、控制分頁引擎、輸出印刷品質的 PDF。無論是排版設計還是理解用戶意圖，Claude 確實是目前最強的模型，所以把收尾交給最強的。

這時手上有：原始 PDF（19 頁、35 張配圖）和文字已定稿的 HTML（一張圖都沒有，配圖位置只有文字佔位框）。

實際使用的 Prompt

這段 Prompt 的特點是：硬規格講死，軟決策留白。A4、頁碼、目錄這些硬規格直接寫死；風格、字級、配色這些品味決策刻意不寫——不是漏寫，而是配合最後一句「詢問我，不要自己來」，預期 AI 動工前帶著具體選項回來問。

計畫模式，與「先看再問」

這個階段用計畫模式啟動：AI 必須先探索、提出完整計畫、經核准後才能動工。AI 在提問前先做了三件偵察：盤點 PDF（35 張不重複圖片的位置與尺寸）、盤點 HTML（53 個章節標題、零圖片）、把關鍵頁渲染成圖片親眼看。第三步帶出整個專案最重要的技術發現：

這個發現直接升級了方案：既然圖是乾淨的、標註座標可以從 PDF 取出，就能「抽乾淨圖＋用 HTML/CSS 重畫標註」——標註從此變成繁體、可放大、可改字型的活文字，而不是糊在圖裡的簡體小字。先看再問的價值就在這裡：AI 帶著「我已經知道圖長怎樣」去提問，選項才會具體可選，而不是空泛的「請問你想要什麼風格？」。

四個由人決定的設計題

偵察完成後，AI 一次提出四個決策題，每題附選項與代價，全部由我來選：

#問題我的選擇為什麼必須人來選
1配圖標註怎麼處理？HTML 重建（繁體、字大，工序多）或整塊裁切原圖（快，但標註仍是簡體小字）HTML 重建工作量與品質的取捨，牽涉交付標準
2設計配色風格？深藍科技感（呼應儀器 UI）或黑白極簡深藍科技感品味與品牌判斷，AI 不應代決
3內文字體放大到多少？16px（預估 24–28 頁）或 18px（更易讀但頁數更多）16px易讀性與頁數成本的取捨
4目錄列到哪一層？章＋節（約 2 頁）或僅章（1 頁）章＋節查找便利性與篇幅的取捨

加上第五個決策點——計畫核准：AI 把答案寫進完整計畫書，核准後才動工。這份計畫書在完工後直接變成驗收清單。

排版管線與踩坑記錄

六步可重跑的管線

實際執行管線每一步都是一支可重跑的腳本：

步驟工具／腳本做什麼
1. 抽圖與取座標extract_assets.py（PyMuPDF）抽出 35 張不重複圖片；記錄每頁圖片位置與文字行座標
2. 計算標註規格build_figures.py找出每張底圖的疊加圖示與標註文字，換算成相對百分比位置
3. 切配件照片extract_accessories.py從 PDF 按座標高解析裁切 23 張配件照
4. 產生新版 HTMLbuild_html.js＋manual.css讀原 HTML（文字一字不動），佔位框換成配圖、標註重畫成繁體、加封面與目錄
5. 分頁與列印Paged.js＋print_pdf.js（puppeteer-core）瀏覽器內自動分頁（A4、頁碼、防跨頁），等分頁完成事件後才列印
6. 驗證PyMuPDF 渲染回 PNG＋程式化斷言逐頁目檢＋自動比對目錄頁碼與實際頁碼

管線設計守兩個原則：資料驅動——33 處標註位置全部從 PDF 程式化算出來，不靠人眼估，否則既慢又不可重現；管線可重跑——任何修改只要改源頭再跑一次指令，60 秒重出成品，後面修了四輪版面問題，每輪成本都極低。另外一個通用心得：時序問題要等「完成事件」，不要等「N 秒」——直接用 headless Chrome 列印曾因為分頁還沒跑完，只印出 5 頁。

總結：三段接力，五條準則

把三個階段放在一起看，AI 的角色、工作性質、Prompt 重點各不相同：

維度階段一：DeepSeek階段二：Codex階段三：Claude Code
AI 的角色生產者審稿者工程師
工作性質翻譯與改寫比對與修正程式化排版管線
Prompt 重點講清楚風險與標準強調「重新檢查、不沿用」硬規格講死、軟決策留白待問
人工守門不確定名詞要問名稱類修改要問設計決策用選擇題問＋計畫核准
驗收方式肉眼看初版回報修正清單對照計畫＋程式斷言＋逐頁目檢

跨階段通用的五條準則：

  • 每階段只做一種性質的工作——產出、質檢、排版分開，Prompt 才能聚焦，問題才能歸因。
  • 上一階段的產物永遠當草稿——每個新階段都明示「不要直接視為正確稿」。
  • 「詢問我，不要自己來」每一階段都要寫——人工守門點是三階段共同的安全網，守的對象從名詞、名稱到設計決策各不相同，原則相同。
  • 要求 AI 先探索、先計畫，再動工——階段三的四個精準選擇題來自動工前的偵察；計畫書同時是事後的驗收清單。
  • 完工不等於交付，複驗才是終點——每一階段結束都有一輪檢查；最後一輪用「程式斷言＋逐頁目檢」雙保險。

回到開頭的工作流理念：計劃、開發、驗證（審稿）、品管、agent 輸出。對於有合規風險、翻譯風險、格式要求的文件，這種分段接力比單次生成穩定得多——第一個 AI 負責產出，第二個 AI 負責質檢，最強的 AI 負責收尾。

提醒：本頁為個人工作流程分享。文中的合規改寫做法（移除醫療行為、疾病診斷、療效宣稱描述）僅為產品文件的編輯實務，實際產品文案是否合規，仍需依當地法規與專業意見判斷。各 AI 工具的功能與介面可能隨版本更新，實際操作請以各官方文件為準。
