01 · Summary · 執行摘要

執行摘要

這個案子的素材是一份 19 頁的簡體中文美容儀器說明書 PDF，最終交付是一份 28 頁 A4、繁體中文、含封面目錄配圖的新版手冊 PDF。以下按 Plan → Rewrite → Dev → QA 四個階段，記錄每一步的判斷邏輯、使用者下的 Prompt、哪些決策必須由人來做。

四個階段各自負責什麼

  • Plan：定義要做什麼、怎麼做、守門點在哪。
  • Rewrite：把原始素材轉成可修改的繁體中文草稿。
  • Dev：修正錯誤並開發可交付的最終成品。
  • QA：確認成品符合計畫與原始目標。
02 · Plan · 案前判斷

Plan：案前判斷與工作計畫

表面任務是「PDF 翻譯成繁體中文 HTML」，但動工前先判斷出這份文件有三個風險，每一個都會讓「直接翻譯」變成錯誤做法：

  • 疑似醫療描述——原稿有大量容易被誤認為醫療行為、疾病診斷、療效宣稱的語句，必須改寫而不是照翻。
  • 簡轉繁陷阱——原稿是簡體中文，不能只做字形轉換，專有名詞與台灣常用語都要深度在地化。
  • 格式保留——說明書有章節、警告、注意事項、表格、配件清單，轉出來不能只剩純文字。

所以這個案子的目標從一開始就定義成：

四階段工作骨架

這個案子的工作骨架是 Plan → Rewrite → Dev → QA。這樣安排有兩個前提，每個階段都要遵守：

  • 每階段只做一種性質的工作——翻譯、質檢、排版分開，Prompt 才能聚焦，出問題才能歸因。
  • 上一階段的產物永遠當草稿——每個新階段都明確告訴 AI「不要直接視為正確稿」，避免錯誤被沿用到底。
階段本案對應工作工具目的
Plan案前風險判斷、目標定義、工具規劃、計畫核准人工 + AI 計畫模式定義要做什麼、怎麼做、守門點在哪
RewritePDF 翻譯、合規改寫、產出 HTML 初版Open Code + DeepSeek V4-pro把原始素材轉成可修改的繁體中文草稿
DevCodex 複驗修正 + Claude Code 配圖排版Codex → Claude Code修正錯誤並開發可交付的最終成品

輸出格式選 HTML 而不是直接做 PDF，是刻意的：HTML 比 PDF 容易事後校正，等內容定稿再轉成 PDF 也很方便。後面 Dev 與 QA 都受惠於這個決定。

03 · Rewrite · 翻譯與合規改寫

Rewrite：翻譯與合規改寫

為什麼選 Open Code + DeepSeek

選它有兩個理由。第一是省 token：PDF 轉 HTML 是大量整理工作，用便宜的模型跑初版最划算。第二個理由更關鍵：原稿是簡體中文，裡面有許多疑似醫療的說明方式，直接調用其他模型時，模型無法分辨這到底是不是真的醫療內容，很容易觸發內容審查、被迫拒絕工作。DeepSeek 能判斷語境，先把內容修正成合規版本，後面的工具才接得下去。

使用者下的 Prompt

這段話不長，但拆開來看，把初版需要的條件一次講齊了：

Prompt 片段目的
pdf檔案為美容儀器說明書給 AI 文件類型與上下文，避免當一般文章處理
內有大量會遭人誤會為醫療行為的敘述指出最重要的合規風險，不只是翻譯問題
請協助修正要求改寫，不是只找問題
不得直接簡轉繁＋深度轉換避免機械字形轉換，要求語意與用語層級的在地化
不確定的名詞不要硬翻譯，詢問我設下人工確認點，避免 AI 自行創造錯誤名稱
保留原有格式，製作成html檔案指定輸出格式與版面保留要求

反過來想就知道為什麼要講這麼齊：只說「幫我翻成繁體中文」，AI 會把「患者」「禁忌症」「醫療裝置」原樣留下；只說「幫我去掉醫療內容」，AI 可能連必要的安全提醒一起刪掉，或把格式打散。

Rewrite 完成後：人工確認清單

DeepSeek 產出 HTML 初版後，不要當完稿，把它當「可編輯草稿」快速確認六件事：

  • 是否真的有產出 HTML 檔案。
  • 章節是否大致完整。
  • 警告、注意、表格、配件清單是否還在。
  • 是否有明顯簡體殘留。
  • 是否有看起來像醫療用語的詞。
  • 功能名稱有沒有被 AI 改得太漂亮、太像療效宣稱。

確認完不要急著交付，進 Dev 階段。

04 · Dev · 複驗與排版

Dev：複驗修正與版面開發

Dev 的第一步把 AI 的角色從「生產者」切換成「審稿者」：不是重做，而是拿原始 PDF 和初版 HTML 對照，找出錯翻、醫療描述殘留、改寫不當，然後修正。工具選 Codex 是習慣用它校稿，換成其他 AI 工具其實不影響這個流程。

A — Codex 複驗校稿

使用者下的 Prompt

這段 Prompt 的關鍵字是「重新檢查」。Dev 複驗最容易犯的錯，是 AI 沿用初版內容、沒有真正回去比對原稿。所以要明確要求：看原始 PDF、看改寫後 HTML、找出問題；能確定的直接修，不確定的停下來問。

複驗實際抓到的問題

初版看起來已經很完整，但 Codex 對照原稿後仍然抓出好幾類問題——這正是「看起來完成，其實殘留風險」的實例：

問題類型例子為什麼要修
醫療裝置語彙「植入式心臟除顫器或其他電磁植入式醫療裝置」太接近醫療器材語境
疾病與生理指標「慢性疾病者（如血糖、血壓、血脂相關問題者）」仍像醫療禁忌或疾病診斷
功能名稱被改寫「五極彩光微電波護理」原 PDF 是「五極彩光微電」，初版自行加了療程感的詞
功能名稱不精準「水氧噴霧」原 PDF 是「水氧噴槍」
功效暗示「煥膚筆」比原名中性，但仍可能暗示膚況改善
繁中錯字或不自然「實銷性」「其它」要改成正式繁中說明書語氣

修正方向：不是刪光，而是換語氣

合規改寫的原則是保留安全提醒、拿掉醫療診斷語氣，讓文件讀起來像美容儀器產品文件，而不是醫療器材文件：

原本的語氣改寫方向
患者、疾病、感染、心臟除顫器使用者、膚況、植入式電子裝置
禁忌症不建議使用情形
血糖、血壓、血脂當日狀態不佳或需避免刺激者
皮膚感染皮膚破損、紅腫、滲液或明顯異常

人工守門點：哪些地方 AI 不能自己定案

三個階段的 Prompt 都寫了同一句話：「不確定的部分詢問我。」這不是客套，而是這類任務裡真正的安全網。需要停下來問人的典型情況：

  • 功能名稱可能和機身 UI、按鈕、配件標籤一致時——改了名，使用者會對不上實物。
  • 原文名稱本身有醫療或功效暗示，但改名可能影響產品辨識時。
  • 某個詞可能是品牌專有名詞，不確定能不能改。
  • 安全提醒到底能刪除、還是只能改寫時。
代表案例
本案留給人工確認的代表案例是「美斑筆」：原名容易被理解為處理斑點、改善色素，初版改成的「煥膚筆」仍有膚況改善暗示，最後改成最中性的「美容筆」——因為這個名稱可能印在機身或包裝上，AI 不自行定案，由使用者確認。

B — Claude Code 配圖與排版

前一步是內容質檢，這一步性質完全不同，是版面工程：整合 PDF 配圖、重新設計排版、輸出 A4 PDF 成品。選 Claude Code 是因為計畫模式可先確認方案再動工，且排版設計與理解用戶意圖能力強，適合這種需要反覆確認的複雜排版任務。

使用者下的 Prompt

這段 Prompt 的特點是：硬規格講死，軟決策留白。A4、頁碼、目錄這些硬規格直接寫死；風格、字級、配色這些品味決策刻意不寫——配合最後一句「詢問我，不要自己來」，預期 AI 動工前帶著具體選項回來問。

四個由人決定的設計題

Claude Code 依計畫模式提出完整方案前，先帶著四個決策題回來問，每題附選項與代價，全部由使用者來選：

#問題使用者的選擇為什麼必須人來選
1配圖標註怎麼處理？HTML 重建（繁體、字大，工序多）或整塊裁切原圖（快，但標註仍是簡體小字）HTML 重建工作量與品質的取捨，牽涉交付標準
2設計配色風格？深藍科技感（呼應儀器 UI）或黑白極簡深藍科技感品味與品牌判斷，AI 不應代決
3內文字體放大到多少？16px（預估 24–28 頁）或 18px（更易讀但頁數更多）16px易讀性與頁數成本的取捨
4目錄列到哪一層？章＋節（約 2 頁）或僅章（1 頁）章＋節查找便利性與篇幅的取捨

加上第五個決策點——計畫核准：Claude Code 把答案寫進完整計畫書，使用者核准後才動工。這份計畫書在完工後直接變成 QA 的驗收清單。

05 · QA · 驗收複驗

QA：驗收複驗

完工不等於交付，最後再下一段複驗 Prompt：

這句話有兩個驗收基準：對照計畫——計畫模式留下的計畫書此刻變成驗收清單，逐項核對；對照目標——「清晰、容易閱讀」回到最初需求的本意，防止做出規格都對但不好讀的成品。本案的驗收項目：

檢查項方法結果
A4 尺寸程式檢查全部頁面尺寸28 頁全部 210×297mm
內文字級程式統計 PDF 字級分布主要內文 12pt（=16px），符合選定值
簡體殘留程式掃描全文比對簡體字表無殘留
頁碼與目錄準確性程式逐頁檢查頁尾；抽 12 個目錄條目與實際頁碼比對全數吻合
圖號連續性程式抽取全部「圖 X-N」驗證遞增無重複連續無重複
段落跨頁、配圖對位、版面品質全 28 頁逐頁目檢無段落被切斷，標註對位正確

QA 可以換成 AI 來做

本案的 QA 是由使用者人工完成的。但這個階段非常適合換成 AI：驗收基準是計畫書，計畫書是文件，AI 可以讀。具體做法：

  • 把計畫書交給 AI，要求逐項比對成品與計畫，有偏差列出並說明原因。
  • 要求 AI 執行可程式化的斷言（尺寸、頁碼、目錄準確性、簡體殘留）。
  • 要求 AI 逐頁渲染成圖後親自看，確認版面品質，而不是只看中間產物。
  • 完成後回報：哪些通過、哪些有偏差、是否還有需要人工判斷的主觀問題。

Plan 階段寫得越清楚，QA 就越容易自動化——計畫書本身就是驗收清單，AI 只需要逐項執行。能程式化的斷言交給程式，只有「好不好讀」這類主觀判斷留給眼睛或由人確認。

08 · Conclusion · 總結

總結：四階段，五條準則

把 Plan → Rewrite → Dev → QA 放在一起看，每個階段的工具、工作性質與守門方式各不相同：

階段工具工作性質人工守門驗收方式
Plan人工 + AI 計畫模式風險判斷與工作定義目標定義、守門規則、計畫核准計畫書核准
RewriteOpen Code + DeepSeek翻譯與合規改寫不確定名詞要問肉眼確認初版六件事
Dev ACodex比對與修正名稱類修改要問回報修正清單
Dev BClaude Code版面工程與成品輸出設計決策用選擇題問＋計畫核准對照計畫＋逐頁目檢
QA人工（可換 AI）驗收複驗主觀品質判斷留給人計畫書對照＋程式斷言＋逐頁目檢

跨階段通用的五條準則：

  • 每階段只做一種性質的工作——翻譯、質檢、排版分開，Prompt 才能聚焦，問題才能歸因。
  • 上一階段的產物永遠當草稿——每個新階段都明示「不要直接視為正確稿」。
  • 「詢問我，不要自己來」每一階段都要寫——人工守門點是四階段共同的安全網，守的對象從名詞、名稱到設計決策各不相同，原則相同。
  • 要求 AI 先計畫，再動工——計畫書同時是事後的驗收清單，Plan 寫得越清楚，QA 就越容易。
  • 完工不等於交付，QA 才是終點——本案 QA 由人工完成，但只要計畫書夠清楚，這一關可以整個交給 AI，人工只需確認主觀品質。

對於有合規風險、翻譯風險、格式要求的文件，Plan → Rewrite → Dev → QA 這種分工比單次生成穩定得多——Rewrite 負責產出草稿，Dev 負責修正與開發，QA 負責驗收，每一關都有明確的守門點與驗收基準。

提醒：本頁為個人工作流程分享。文中的合規改寫做法（移除醫療行為、疾病診斷、療效宣稱描述）僅為產品文件的編輯實務，實際產品文案是否合規，仍需依當地法規與專業意見判斷。各 AI 工具的功能與介面可能隨版本更新，實際操作請以各官方文件為準。
