01發想與定位

先把「不滿」翻譯成產品任務。

PCShop 的起點很具體：傳統電腦估價網站太像舊式表格，手機難用，新手又怕 CPU、主機板、記憶體、機殼尺寸選錯。主編要做的第一件事，不是叫 AI 寫頁面，而是把這句抱怨整理成清楚的專案命題。

原始痛點

使用者懂預算與用途，卻不一定懂 socket、瓦數、DDR4/DDR5 或顯示卡長度。傳統清單把所有責任丟給使用者，導致「看得到零件，卻不確定能不能買」。

產品任務

建立一個手機優先的本地電腦店估價工具：八大零件逐步選、硬衝突立即阻擋、軟警告清楚提示、CPU+GPU 選定後顯示 3DMark Time Spy 預估等級。

1

寫下真實情境

「手機上挑電腦」「怕買錯」「店家需要可分享估價單」比抽象的「做購物網站」更有方向。

2

定義使用者

新手需要保護式引導；DIY 玩家需要快速篩選、本地庫存與即時相容性判斷。兩者都不想讀一整本硬體百科。

3

建立文件骨幹

PRODUCT.md 寫產品意圖與體驗原則；規格書.txt 寫資料結構、相容性規則、UI 行為與後台要求。

02主編計畫

先要求 AI 做計畫，確認後才執行。

好的 AI 協作不是「請幫我做一個網站」就結束，而是先讓 AI 讀材料、列假設、提出成功標準。計畫是專案的安全帶：它讓人知道現在要做什麼，也讓 AI 知道哪些事不能亂猜。

A

交付材料

提供 teaching.txt、產品概念、規格書、既有網頁風格參考，讓 AI 先讀懂「內容」和「出版形式」。

B

明確要求停在計畫

指令中寫清楚：「你作為出版社主編輯，先設計計劃，確認後再執行。」這會迫使 AI 先說明取捨，不會直接改檔。

C

確認約束

本次確認了檔名、工具要明確列出、非官方技能和外掛要附來源連結、風格要參考既有 making-of.html。

幫我做一個 PCShop 教學網頁。
問題：沒有讀者、沒有素材、沒有驗收標準，也沒有說要不要先確認。
你作為出版社主編輯，先設計計劃，確認後再執行。
請讀 teaching.txt、PRODUCT.md、規格書.txt，
把 PCShop 製作流程做成單檔動態 HTML。
明確列出使用的工具、技能與外掛；
非官方項目請附來源連結。
風格參考 making-of.html，完成後推送到 GitHub Pages。
好處：角色、流程、素材、格式、工具揭露、風格與交付方式都清楚。
03過濾建構

相容性不是寫死，
而是先把規則資料化。

PCShop 的核心不是商品清單，而是「保護新手不要選錯」。所以第一步不是寫很多 if/else，而是把每個零件會影響相容性的欄位整理出來，再用一張約束表描述跨類別規則。

① 先決定每個類別需要哪些欄位

類別過濾需要看的欄位用途
CPUsocket、tdp、memory_type決定主機板腳位、記憶體類型與電源瓦數餘裕。
主機板socket、memory_type、form_factor對齊 CPU、RAM，並檢查機殼支援尺寸。
顯示卡length_mm、tdp、power_connector檢查機殼能不能裝、電源是否足夠。
機殼 / 電源max_gpu_length_mm、wattage把尺寸和瓦數變成可計算條件。

② 把相容性規則做成約束表

sourcetarget條件類型提示
CPU主機板CPU.socket = MB.socket硬衝突CPU 與主機板腳位不符。
主機板記憶體MB.memory_type = RAM.memory_type硬衝突記憶體規格不符合主機板。
顯示卡機殼GPU.length_mm <= Case.max_gpu_length_mm硬衝突顯示卡長度超出機殼限制。
CPU + GPU電源PSU.wattage >= tdp_sum + 150軟警告電源餘裕偏低，建議升級。
1. 讀取已選零件例如使用者已選 LGA1700 CPU，就把 socket=LGA1700 當成條件來源。
2. 找目標類別規則切到主機板頁時，只拿「目標是主機板」的規則，不掃全部資料。
3. 產生可買清單智慧過濾開啟時，只顯示可直接加入的零件；新手不會誤選。
4. 回報不可買原因智慧過濾關閉時，不相容品保留但灰階，並顯示被哪條規則擋住。
教學用偽程式
function filterProducts(category, selectedParts, smartFiltering) {
  const rules = constraints.filter(rule => rule.target === category);
  return products
    .filter(product => product.category === category)
    .map(product => ({ product, conflicts: checkRules(product, selectedParts, rules) }))
    .filter(row => !smartFiltering || row.conflicts.every(c => !c.isHard));
}

主編提醒

教初學者時，先教「資料怎麼長」再教「程式怎麼寫」。因為過濾引擎的難點不是語法，而是有沒有把真實世界的相容性轉成穩定欄位與可追蹤規則。

04版面設計

版面從使用姿勢開始，
不是從漂亮卡片開始。

PCShop 是手機優先工具，所以版面設計先問：使用者單手拿手機時，最常做什麼？答案是看進度、切類別、加入零件、修正錯誤。因此頁面要圍繞這四件事，而不是把桌機表格硬縮成手機版。

手機主流程線框

PCShop Quote
組裝進度CPU ✓　主機板待選　GPU ✓　PSU 警告
3DMark Time SpyCPU + GPU 選定後顯示效能等級
零件挑選列產品名稱、價格、庫存、相容性提示
進度挑零件估價單
1

底部導覽

手機拇指容易碰到的位置放三個主工作：組裝進度、零件挑選、我的估價單。

2

進度總覽優先

新手最怕忘記還缺什麼，所以進度區要能顯示完成、待選、警告，並能直接替換或移除。

3

產品列取代密集表格

每個零件先露出名稱、價格、庫存與重點規格；完整規格用展開層承接。

設計決策對照

設計問題PCShop 的做法原因
如何降低新手焦慮？預設智慧過濾，只顯示可加入零件。少看不相關選項，比一次給完整表格更友善。
如何讓 DIY 玩家保有自由？提供「智慧過濾關閉」狀態，不相容品仍可看見。進階使用者可以理解原因並自行判斷。
如何避免手機擁擠？列表只放決策資訊，詳細規格點開才看。行動版重點是快速判斷，不是展示所有資料。
如何讓估價更像店員？用平實文字說明硬衝突與軟警告。提示應該解決問題，不應丟出硬體術語考使用者。

版面設計口訣

先排工作流，再排元件；先保護新手，再提供進階自由；先讓手機好用，桌機只是把資訊變得更密，不改變使用邏輯。

05店家後台

前台給客人用，
後台給店家維護資料。

PCShop 不只是一個展示頁，它要讓店家能維護商品。後台的設計原則很清楚：不要把管理入口放在顧客商店頁；入口只寫在 README 或維護文件裡，前台維持乾淨的估價流程。

1

保留登入接口

MVP 階段可以暫時不要求帳密，但仍保留 login / session API。未來要接真實帳密時，不需要重做整個管理流程。

2

搜尋、修改、寫回 CSV

後台不是假的表單。新增、編輯、刪除產品後，要真正寫回 data/products.csv，讓前台下次讀到同一份資料。

3

入口只給維護者

顧客不需要看到「管理後台」。把 admin.html 的使用方式放在 README，商店頁不放按鈕。

後台最小架構

server.js 提供 session 與 /api/products CRUD；admin.html 是維護畫面；admin.js 處理搜尋與表單；admin.css 維持後台介面清楚。

搜尋欄位應包含 ID、品名、分類、庫存、價格、tags、badges、restriction、tone，讓店家可以快速找到要改的資料列。

後台資料流
admin.html → admin.js → /api/products → server.js
                                      ↓
                              data/products.csv
                                      ↓
                              index.html 前台重新讀取

教學重點

後台不是「多做一頁」而已，它是營運入口。初學者要學會區分顧客路徑與維護者路徑：顧客只看到估價；店家才看到資料管理。

06維護紀律

每次改功能，
文件也要跟著升版。

PCShop 的長期維護靠兩份文件撐住：PRODUCT.md 說明產品意圖與體驗原則；規格書.txt 說明功能、資料、相容性、UI 與後台規則。只改程式不改文件，幾次之後專案就會失去方向。

什麼變更要同步文件？

變更類型同步位置原因
產品目的、使用者體驗、設計原則PRODUCT.md讓後續設計知道產品為誰服務、哪些體驗不能破壞。
相容性、過濾、資料結構、後台行為規格書.txt讓功能邏輯有可追蹤的規格來源。
功能同時影響體驗與邏輯兩份都更新例如 3DMark 預覽、估價單輸出、後台 CRUD，都同時影響產品與實作。
維護者入口或操作方式README.md讓維護者知道怎麼啟動、測試、進入後台，但不打擾顧客前台。
1. 改功能前先讀 PRODUCT.md、規格書.txt、AGENTS.md，確認約束。
2. 改功能時程式與文件同一批處理，不把規格更新留到「之後再補」。
3. 驗證時用本機頁面、CSV 檢查、Node 語法檢查或瀏覽器測試留下證據。
4. 推送時只提交本次相關檔案，避免把別人的未完成修改一起包進 commit。

版本號的作用

版本與日期不是形式主義。它讓維護者知道：現在這份程式碼對應哪一版產品概念、哪一版功能規格。當未來出現衝突，就能回頭查「這個行為是在哪次決策被寫進去的」。

08溝通與修正

把 AI 當成同事，不是許願池。

修正時最有效的做法，是把問題描述成可觀察狀態，然後要求 AI 實測。不要只說「幫我美化」，而是說「手機版工具卡太擠，請縮小內距並用瀏覽器確認沒有橫向溢位」。

描述問題→指定驗證→AI 修改→瀏覽器檢查→推送

好修正

「工具卡的官方/第三方標籤要更醒目，手機版不能換行到壓住文字。請改完後用 390px 寬度驗證。」

難修正

「整體再高級一點。」這句沒有錯，但它不是可驗證指令。AI 只能猜你的美感方向，最後容易越改越遠。

主編輯檢查清單

每次要求修正，都問三件事：讀者會不會更容易理解？修改是否符合原本風格？有沒有用實際頁面驗證？這三題比「多加一點動畫」更重要。

10完成

完成不是「寫完」，
而是可閱讀、可驗證、可追蹤。

✓有清楚的產品起點：手機優先、避免相容性錯誤、本地店家可用。
✓有主編計畫：先確認目標、讀者、素材、風格與驗收標準。
✓有過濾引擎教學：欄位、約束表、智慧過濾與衝突回報都能說清楚。
✓有版面設計教學：從手機使用姿勢推導出進度、挑選與估價單三個主區。
✓有店家後台教學：管理入口不放前台，CRUD 真正寫回產品資料。
✓有維護紀律：功能變更同步 PRODUCT.md、規格書.txt、README 與版本日期。
✓有工具揭露：官方、本地、第三方來源分清楚。
✓有互動教學：Prompt 對照、流程步驟、複製指令、完成清單。
✓有上線流程：本機驗證、commit、push、GitHub Pages 展示。
