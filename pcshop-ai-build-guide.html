從一句抱怨，

這是 PCShop 電腦組裝估價系統的製作筆記。從「組裝電腦不知道怎麼搭」這個老問題出發，記錄整個流程：先用 DeepSeek 把模糊想法聊成大綱與初版規格書，再交給 Codex 規劃設計、做出雛型、寫程式、用瀏覽器驗證，最後部署成可分享的網站。寫給同樣在玩 AI 工具的新手同好參考。

01發想與定位

先把「不滿」翻譯成產品任務。

買組裝電腦最頭痛的，往往不是預算或用途，而是不知道怎麼搭：要做一堆功課、到處比價找心得，最後還得去論壇貼配單請人指教。雖然現在有原價屋、欣亞這類線上估價單，但風格像二十年前的產物，找產品慢、不知道搭出來有沒有問題，用手機更是難操作。於是我想：能不能做一個會自動篩掉不相容零件、自動擋掉常見錯誤、還能直接秀出效能等級的線上估價單？PCShop 就是這樣開始的。

原始痛點

使用者懂預算與用途，卻不一定懂 socket、瓦數、DDR4/DDR5 或顯示卡長度。傳統清單把所有判斷丟回給使用者，結果「看得到零件，卻不確定能不能買」。

產品任務

做一個手機優先的本地電腦店估價工具：八大零件逐步選、硬衝突當場擋、軟警告講清楚、選好 CPU+GPU 後直接顯示 3DMark Time Spy 預估等級。

目標使用者

使用者核心痛點需要什麼
電腦新手不懂 socket 腳位、DDR 世代差異，怕買到不相容零件保護式引導：預設只顯示相容選項，衝突時說明原因
DIY 玩家懂自己要什麼，卻苦於傳統表格速度慢、手機更難操作快速過濾 + 本地庫存即時查詢 + 相容性警告
電腦店店家估價靠人工核對，缺乏讓客人自助挑選的工具可維護的商品後台與可分享的估價單連結
1

寫下真實情境

「手機上挑電腦」「怕買錯」「店家要能給可分享估價單」，比抽象的「做購物網站」更有方向。

2

定義使用者

新手要保護式引導；DIY 玩家要快速篩選、本地庫存與即時相容性判斷。兩種人都不想讀一整本硬體百科。

3

先聊出大綱

用 DeepSeek 的聊天功能把想法討論成整體大綱，再整理成初版 規格書.txt 與 PRODUCT.md，當作後續開發的依據。

02協作規劃

先讓 AI 做計畫，確認後才動手。

我的做法不是丟一句「幫我做個網站」就等結果，而是分兩棒：DeepSeek 負責把模糊想法聊成大綱、產出初版規格書；Codex 拿到規格書後，先規劃整個設計流程讓我審閱，我改過一輪，再請它把網站雛型補完。計畫是專案的安全帶——讓人知道現在在做什麼，也讓 AI 知道哪些事不能亂猜。

A

交付材料

把產品概念、初版規格書、既有網頁風格參考交給 AI，先讓它讀懂「內容」和「想要的形式」。

B

先停在計畫

明確要求「先把執行計劃做出來，確認後再動手」，讓 AI 先講假設與取捨，目標一致了才改檔案。

C

這次先講好檔名、工具要明確列出、非官方技能和外掛要附來源連結、風格參考既有 making-of.html。

03過濾建構

相容性不是寫死，
而是先把規則資料化。

PCShop 的核心不是商品清單，而是「保護新手不要選錯」。我採用的方式是：每個零件建檔時就輸入規格標籤——CPU 的插槽類型、顯卡的瓦數與長度、機殼能容納的顯卡長度與散熱器高度等等。選單再依這些標籤過濾，讓不相符的產品不會被選進來，避免 AMD 的 CPU 配到 Intel 主機板，或買了機殼結果顯卡裝不下這種事。

① 先決定每個類別需要哪些欄位

類別過濾需要看的欄位用途
CPUsocket、tdp、memory_type決定主機板腳位、記憶體類型與電源瓦數餘裕。
主機板socket、memory_type、form_factor對齊 CPU、RAM，並檢查機殼支援尺寸。
顯示卡length_mm、tdp、power_connector檢查機殼能不能裝、電源是否足夠。
機殼 / 電源max_gpu_length_mm、wattage把尺寸和瓦數變成可計算條件。

② 把相容性規則做成約束表

sourcetarget條件類型提示
CPU主機板CPU.socket = MB.socket硬衝突CPU 與主機板腳位不符。
主機板記憶體MB.memory_type = RAM.memory_type硬衝突記憶體規格不符合主機板。
顯示卡機殼GPU.length_mm <= Case.max_gpu_length_mm硬衝突顯示卡長度超出機殼限制。
CPU + GPU電源PSU.wattage >= tdp_sum + 150軟警告電源餘裕偏低，建議升級。
1. 讀取已選零件例如使用者已選 LGA1700 CPU，就把 socket=LGA1700 當成條件來源。
2. 找目標類別規則切到主機板頁時，只拿「目標是主機板」的規則，不掃全部資料。
3. 產生可買清單智慧過濾開啟時，只顯示可直接加入的零件；新手不會誤選。
4. 回報不可買原因智慧過濾關閉時，不相容品保留但灰階，並顯示被哪條規則擋住。
5. 列出必需種類把組裝必需的種類都列在進度區，使用者一眼看到還缺什麼，少了散熱器開不了機這種事就不會發生。

一個小心得

先想清楚「資料怎麼長」，再想「程式怎麼寫」。過濾引擎難的不是語法，而是有沒有把真實世界的相容性，變成穩定的欄位與可追蹤的規則。

04版面設計

版面從使用姿勢開始，
不是從漂亮卡片開始。

PCShop 是手機優先的工具，所以我更在意 UX 而不是 UI。手機頁面小，我把資訊拆成三個頁簽，把不必占用畫面的東西移到別處，讓使用者專心挑零件。版面圍繞單手使用最常做的四件事：看進度、切類別、加入零件、修正錯誤——而不是把桌機表格硬縮成手機版。

手機主流程線框

PCShop Quote
組裝進度CPU ✓　主機板待選　GPU ✓　PSU 警告
3DMark Time SpyCPU + GPU 選定後顯示效能等級
零件挑選列產品名稱、價格、庫存、相容性提示
進度挑零件估價單
1

底部導覽

手機拇指容易碰到的位置放三個主工作：組裝進度、零件挑選、我的估價單。

2

進度總覽優先

新手最怕忘記還缺什麼，所以進度區要能顯示完成、待選、警告，並能直接替換或移除。

3

產品列取代密集表格

每個零件先露出名稱、價格、庫存與重點規格；其餘刻意收起，只留關鍵訊息，並附官方頁面連結，讓人用最少力氣挑到適合的產品，完整規格用展開層承接。

設計決策對照

設計問題PCShop 的做法原因
如何降低新手焦慮？預設智慧過濾，只顯示可加入零件。少看不相關選項，比一次給完整表格更友善。
如何讓 DIY 玩家保有自由？提供「智慧過濾關閉」狀態，不相容品仍可看見。進階使用者可以理解原因並自行判斷。
如何避免手機擁擠？列表只放決策資訊，詳細規格點開才看。行動版重點是快速判斷，不是展示所有資料。
如何讓估價更像店員？用平實文字說明硬衝突與軟警告。提示應該解決問題，不應丟出硬體術語考使用者。

關於配色

產品本身的配色，我參考了華碩、蘋果這類大廠購物頁的調性——沉穩靛藍當品牌色、青藍當「相容／通過」的輔助色，想給人簡約、專業、不複雜的感覺，符合 PRODUCT.md 定的「沉穩、精準、守護」。整體原則就一句：先排工作流再排元件，先保護新手再給進階自由，先讓手機好用、桌機只是把資訊變得更密。

05店家後台

前台給客人用，
後台給店家維護資料。

PCShop 不只是一個展示頁，它要讓店家能維護商品。後台的原則很清楚：不要把管理入口放在顧客商店頁；入口只寫在 README 或維護文件裡，前台維持乾淨的估價流程。

1

保留登入接口

MVP 階段可以暫時不要求帳密，但仍保留 login / session API。未來要接真實帳密時，不需要重做整個管理流程。

2

搜尋、修改、寫回 CSV

後台不是假的表單。新增、編輯、刪除產品後，要真正寫回 data/products.csv，讓前台下次讀到同一份資料。

3

入口只給維護者

顧客不需要看到「管理後台」。把 admin.html 的使用方式放在 README，商店頁不放按鈕。

後台最小架構

server.js 提供 session 與 /api/products CRUD；admin.html 是維護畫面；admin.js 處理搜尋與表單；admin.css 維持後台介面清楚。

搜尋欄位應包含 ID、品名、分類、庫存、價格、tags、badges、restriction、tone，讓店家可以快速找到要改的資料列。

後台資料流
admin.html → admin.js → /api/products → server.js
                                      ↓
                              data/products.csv
                                      ↓
                              index.html 前台重新讀取

一個營運上的分界

後台不是「多做一頁」而已，它是營運入口。這裡的關鍵是把顧客路徑和維護者路徑分開：顧客只看到估價；店家才看到資料管理。

06維護紀律

每次改功能，
文件也要跟著升版。

PCShop 的長期維護靠兩份文件撐住：PRODUCT.md 說明產品意圖與體驗原則；規格書.txt 說明功能、資料、相容性、UI 與後台規則。只改程式不改文件，幾次之後專案就會失去方向。

什麼變更要同步文件？

變更類型同步位置原因
產品目的、使用者體驗、設計原則PRODUCT.md讓後續設計知道產品為誰服務、哪些體驗不能破壞。
相容性、過濾、資料結構、後台行為規格書.txt讓功能邏輯有可追蹤的規格來源。
功能同時影響體驗與邏輯兩份都更新例如 3DMark 預覽、估價單輸出、後台 CRUD，都同時影響產品與實作。
維護者入口或操作方式README.md讓維護者知道怎麼啟動、測試、進入後台，但不打擾顧客前台。
1. 改功能前先讀 PRODUCT.md、規格書.txt、AGENTS.md，確認約束。
2. 改功能時程式與文件同一批處理，不把規格更新留到「之後再補」。
3. 驗證時用本機頁面、CSV 檢查、Node 語法檢查或瀏覽器測試留下證據。
4. 推送時只提交本次相關檔案，避免把別人的未完成修改一起包進 commit。

版本號的作用

版本與日期不是形式主義。它讓維護者知道：現在這份程式碼對應哪一版產品概念、哪一版功能規格。當未來出現衝突，就能回頭查「這個行為是在哪次決策被寫進去的」。

08溝通與修正

把 AI 當成同事，不是許願池。

整個專案最難的地方，其實是「改進消費體驗」：購物按鈕怎麼點、選錯了怎麼修正、當下該顯示什麼、又有哪些不必顯示。好設計不是資訊堆滿或畫面花俏，而是讓人用最快、最輕鬆的方式，迎接屬於自己的新電腦。改 AI 的產出時也一樣——把問題描述成可觀察的狀態，再要求它實測。不要只說「幫我美化」，而是說「手機版工具卡太擠，請縮小內距並用瀏覽器確認沒有橫向溢位」。

描述問題→指定驗證→AI 修改→瀏覽器檢查→推送

好修正

「工具卡的官方/第三方標籤要更醒目，手機版不能換行到壓住文字。請改完後用 390px 寬度驗證。」

難修正

「整體再高級一點。」這句沒有錯，但它不是可驗證指令。AI 只能猜你的美感方向，最後容易越改越遠。

我每次改之前會先問自己

每次要求修正，先問三件事：使用者會不會更容易理解？修改是否符合原本風格？有沒有用實際頁面驗證？這三題比「多加一點動畫」更重要。
